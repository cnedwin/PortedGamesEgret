# 《雾汀渡》的两份首稿

《河湾筑家》从[《桃溪县令》](https://github.com/cnedwin/PortedGamesEgret/tree/d82e0abc18ba7ec8352bbedab48f587f8f63e05d/PeachCreek)提取了一个经营决定：玩家替等候的人挑一块地，在选定的位置盖房，并看着住户走到门前。为了观察这套入口能否帮助创作者做出另一款游戏，我们给两个独立会话同一句新需求。

> 做一个叫《雾汀渡》的江南渡口经营小游戏，让玩家给摆渡人搭起第一座船棚，接上第一位等船的客人。

| | A · 通用入口 | B · 经营入口 |
|---|---|---|
| 开场和第一个操作 | 页头下是渡口，右侧是手记。第 4、8 秒分别在河岸取木料、割芦苇。 | 河岸有三个命名地块，旁边是账本。第 4 秒选了柳荫，木架预览随即出现在原地。 |
| 操作后看到的变化 | 第 12 秒在指定空地搭起船棚，第 16 秒请客人上船。第 19 秒提示客人已坐稳，已渡人数仍为零。 | 第 8 秒确认在柳荫动工，木料从 12 降至 4。第 12 秒接客后，载着人的渡船驶向对岸。第 19 秒已到北岸，已渡 1 人、收入 3 枚。 |
| 提交的编辑量（上限 24,000 字节） | 30,213 字节，超限 | 31,019 字节，超限 |

两份首稿均保留模型原始输出，都超过了编辑预算。录像可以比较这两份原稿在同一操作规则下的实际表现。本次只有一对样本，真人参与者为零；玩家能否独立理解玩法、这种改善能否重复，仍待观察。B 虽然拿到了样板的 PNG，但实际用 `src/scenery.mjs` 重新绘制了渡口，也无法从录像单独推断素材、场景结构或指引各起了多大作用。

两份首稿都保留了页头、框内地图和右侧常驻手记。经营入口把“在哪盖”和原地预览带进了首稿，网页式构图也依然存在。公开指引现已加入“收起侧栏看开场、把提示贴近作用对象”的检查，并给生成工程补上了 AGENTS.md 入口。这两项改动发生在采集之后，尚未用新一轮生成验证。

## 生成和复看条件

两次均使用 `gpt-6.2-sol` 和中等推理，限一次回复，生成时没有工具和运行反馈。两端的起始材料上限同为 120,000 字节，A 实际收到 66,355 字节，B 收到 35,091 字节。两端分别使用相应入口的工程和指引，共用同一段 API 说明与同一份 `91f350b` 引擎。编辑量按每项文件路径、查找串、替换内容的 UTF-8 字节总和计算。归档中的首稿未经人工修改，可直接从收录文件提供网页服务。包内继承的模板测试和品质说明描述的是样板本身。

两段无声录像均在 Windows 的 Chrome for Testing 157 上使用软件 WebGL2，画面为 960 × 540，从干净存储开始导航，连续录制 20 秒，包含加载时间。脚本在第 4、8、12、16 秒各有一次根据可见线索进行操作的机会。时间反映这条录像路线。解压任一 ZIP 后，在目录内运行 `python -m http.server 8000` 并打开 `http://localhost:8000/`。比较两版时分别使用新的浏览器配置或不同端口，避免存档串用。
