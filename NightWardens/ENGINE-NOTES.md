# 引擎笔记 · Engine notes

做这款游戏时发现的新白鹭引擎（提交 `a778bed`）的缺陷与建议，格式见 [docs/GAME-STANDARD.md](../docs/GAME-STANDARD.md) 第 3 节。

The faults found in the new Egret engine (commit `a778bed`) while making this game, and suggestions, written as in
part 3 of [docs/GAME-STANDARD.md](../docs/GAME-STANDARD.md).

### 1. 动画控制器的标记名不能重复，报错却没说 · A sequence controller refuses repeated marker ids without saying so — 已写入文档 / documented
<!-- engine-note: {"id": "NightWardens#1", "status": "documented", "topic": "sequence-marker-ids", "workaround": ["src/view/field.mjs"]} -->

- **现象 · What happens**：`createSequenceController(engine, scope, bitmap, clip, { profile: 'egret.sequence-control/1', markers: [{ id: 'step', timeSeconds: 0 }, { id: 'step', timeSeconds: 0.45 }] })` 抛出 `ANIMATION_OPTIONS_INVALID`，信息是「给动画协调器的选项无效：缺了、类型不对或超出范围」。真正的原因是两个标记都叫 `step`：`captureOptions`（`animation/sequenceInput.js`）要求标记名各不相同、符合 `^[A-Za-z][A-Za-z0-9_.-]{0,63}$`、时间不超过片段长度，但这三条都报同一个码，没有哪一条、第几个标记的线索。本作给首领的左右脚各放一个落地标记时撞上，首领一出场整页报错。 · Passing two markers both named `step` throws `ANIMATION_OPTIONS_INVALID` ("one is missing, of the wrong type or out of range"). The real cause is the repeated id: `captureOptions` wants ids that differ, match `^[A-Za-z][A-Za-z0-9_.-]{0,63}$` and fall within the clip, and reports all three with the same code and no hint of which rule or which marker. The game met it with a footfall marker for each of a warden's feet, and the page failed as the warden came.
- **绕过办法 · Workaround**：标记改名为 `stepLeft` 和 `stepRight`（`src/view/field.mjs` 的 `makeWarden`）。 · The markers are named `stepLeft` and `stepRight` (`makeWarden` in `src/view/field.mjs`).
- **建议 · Suggestion**：在错误的 `details` 里写出哪一条规则和标记的下标（如 `{ marker: 1, reason: 'duplicate-id' }`），或给重名单独一个码（如 `ANIMATION_MARKER_DUPLICATE`）；`SequenceMarker` 的类型注释写明「同一控制器内 id 不可重复」。 · Name the rule and the marker's index in the error's details (such as `{ marker: 1, reason: 'duplicate-id' }`), or give a repeated id its own code; say in the `SequenceMarker` type that ids must differ within one controller.
- **状态 · Status**：已写入文档（引擎 #485，`8637ace`）：引擎把这条写成 guide 卡片 sequence-markers；重复的标记名仍被拒绝，报错仍不指明是哪一个。 · Documented (engine #485, `8637ace`): the engine wrote this up as its sequence-markers guide card; a repeated marker id is still refused without saying which.

### 2. 整屏的图在软件渲染下每张约 16 ms · A full-screen picture costs about 16 ms a frame under software rendering — 已写入文档 / documented
<!-- engine-note: {"id": "NightWardens#2", "status": "documented", "topic": "still-layer-cache", "workaround": ["src/art/atlas.mjs", "src/screens.mjs", "src/main.mjs"]} -->

- **现象 · What happens**：在无头 Chromium（SwiftShader，2 核）里，540×960 的守城画面最忙时 p50 66.6 ms、p95 83.4 ms，而脚本每帧只花约 2 ms。逐层隐藏量出：路面（整屏位图）、暗角（整屏半透明）、路口的雾（几十个大而淡的粒子）各约 16 ms；舞台整个隐藏后回到 16.7 ms。另外，把路面做成 WebGL 画布元素自己的 CSS 背景图时，图没有画出来（纯色和渐变能画出来），所以模板「背景交给页面」的做法对图片不直接适用。 · In headless Chromium (SwiftShader, two cores) the busiest watch on a 540 × 960 stage ran at p50 66.6 ms and p95 83.4 ms while the scripts took about 2 ms a frame. Hiding layers one by one showed the road (a full-screen bitmap), the dark edge (full-screen and translucent) and the mist (dozens of large faint particles) at about 16 ms each; with the stage hidden the frame was back to 16.7 ms. Also, a CSS background picture set on the WebGL canvas element itself was not drawn (colours and gradients were), so the template's "let the page draw the backdrop" works for gradients but not directly for pictures.
- **绕过办法 · Workaround**：暗角画进路面；路面用 `src/art/atlas.mjs` 的 `roadUrl` 画一次成图片，作为画布下面一个独立元素 `#road` 的 CSS 背景，按场地在舞台上的位置和大小摆好（`src/screens.mjs` 的 `roadBackdrop`），`#road` 用 `ResizeObserver` 跟着画布的尺寸（`src/main.mjs`）；画布清成透明（`clearAlpha: 0`）；雾减到 24 个粒子；闪光层不用时隐藏；震屏改为用 CSS 平移画布和 `#road`。同类场景降到 p50 33.3 ms；再去掉一层与帧图重复的影子位图后 p50 16.7 ms。 · The edge is painted into the road; the road is painted once by `roadUrl` and shown as the CSS background of `#road`, an element of its own under the canvas, placed and sized to the field on the stage and following the canvas through a `ResizeObserver`; the canvas clears to nothing; the mist is down to 24 particles; the flash hides when unused; the shake moves the canvas and `#road` by CSS. A like scene went to p50 33.3 ms, and to 16.7 ms once a layer of shadow bitmaps that repeated the frames' own shadows was gone.
- **建议 · Suggestion**：`createBrowserGame` 可以提供一个 `backdrop` 选项（一张图或一个画布，引擎在画布下放一个元素、跟着 `fit` 摆好，并提供把舞台矩形换算成它的背景位置的办法），让静态的整屏背景不进每一帧；在 `frame-budget` 卡片里写明软件渲染下整屏半透明层的代价，以及「CSS 背景图放在画布下的元素上，而不是画布元素自己身上」。 · `createBrowserGame` could take a `backdrop` (a picture or a canvas): an element under the canvas, placed with `fit`, and a way to turn a stage rectangle into its background position, so a still full-screen backdrop leaves the frame. The `frame-budget` card could state the cost of full-screen translucent layers under software rendering, and that a background picture belongs on an element under the canvas rather than on the canvas element.
- **状态 · Status**：已写入文档（引擎 #485，`8637ace`）：引擎把这条写成 guide 卡片 still-background（实测后写入）。 · Documented (engine #485, `8637ace`): the engine wrote this up, measured again, as its still-background guide card.

### 3. `createBrowserGame` 的对象冻结且不给画布 · The object of `createBrowserGame` is frozen and has no canvas — 已写入文档 / documented
<!-- engine-note: {"id": "NightWardens#3", "status": "documented", "topic": "browser-game-canvas", "workaround": ["src/main.mjs"]} -->

- **现象 · What happens**：`createBrowserGame` 返回的对象是冻结的（`Object.freeze`），上面没有 `canvas`。游戏要移动画布（震屏）、给画布下的元素对齐尺寸，只能自己留着传进去的那个画布；写 `game.canvas = canvas` 会抛 `TypeError: Cannot add property canvas, object is not extensible`。 · The object it returns is frozen and has no `canvas`. To move the canvas (a shake) or size an element to it, a game has to keep the canvas it passed in; `game.canvas = canvas` throws `TypeError: Cannot add property canvas, object is not extensible`.
- **绕过办法 · Workaround**：画布留在游戏自己的 `app.canvas` 上（`src/main.mjs` 的 `boot`）。 · The game keeps the canvas as its own `app.canvas` (`boot` in `src/main.mjs`).
- **建议 · Suggestion**：给 `BrowserGame` 加一个只读的 `canvas`（和 `stage`、`loop` 一样），或在文档里写明冻结和「自己留着画布」。 · Give `BrowserGame` a read-only `canvas`, as it has `stage` and `loop`, or say in the docs that it is frozen and the game keeps its canvas.
- **状态 · Status**：已写入文档（引擎 #485，`8637ace`）：引擎把这条写成 guide 卡片 camera-page-layer：`createBrowserGame` 的结果没有画布，游戏自己留着；`toStage` 只做页面到舞台。 · Documented (engine #485, `8637ace`): the engine wrote this up as its camera-page-layer guide card: the browser game has no canvas, which the game keeps; `toStage` goes page to stage only.
